# 交易客户端需求

## 1. 项目目标

构建一个独立运行的交易客户端。

客户端从交易策略服务器获取交易信号，并根据服务器给出的交易方向，通过 TqSdk 获取实时行情并执行实际交易。

客户端不负责交易策略计算。

---

## 2. 系统职责

客户端负责：

* 向服务器提交交易品种
* 获取服务器交易信号
* 接收服务器的新信号通知
* 获取 TqSdk 实时行情
* 根据服务器信号执行开仓 / 平仓
* 记录交易信号执行状态
* 防止同一个交易信号重复执行
* 记录交易执行结果
* 管理客户端运行状态

客户端不负责：

* K 线策略计算
* 判断做多还是做空
* 修改服务器策略
* 根据自己的算法产生交易信号

交易方向由服务器决定。

---

## 3. 技术栈

主要技术：

* Python
* TqSdk
* SQLite

服务器通信：

* HTTP API
* 服务端信号通知机制

具体通信方式应优先保持简单可靠。

---

## 4. 核心业务流程

```text
Client
  │
  │ 提交交易品种
  ▼
Server
  │
  │ 产生交易信号
  ▼
Client 收到通知
  │
  │ 获取完整信号
  ▼
检查 SQLite
  │
  ├── 已执行 → 忽略
  │
  └── 未执行
          ↓
     获取实时行情
          ↓
     执行交易
          ↓
     保存执行结果
```

---

## 5. 交易信号

客户端从服务器获取：

```text
signal_id
symbol
direction
position
created_at
```

客户端必须使用 `signal_id` 判断信号是否已经处理。

---

## 6. 交易执行

服务器只负责告诉客户端目标交易方向。

实际成交价格由客户端通过 TqSdk 获取实时市场价格。

因此：

```text
Server
→ 决定做多 / 做空

Client
→ 获取当前市场价格
→ 执行交易
```

服务器提供的价格不能作为客户端实际成交价格的唯一依据。

---

## 7. 信号执行规则

### 新信号

收到新信号后：

1. 查询 SQLite。
2. 判断 `signal_id` 是否已经执行。
3. 如果已经执行，直接忽略。
4. 如果没有执行，获取实时行情。
5. 根据服务器信号执行交易。
6. 记录执行结果。

---

## 8. 防止重复交易

这是客户端最重要的业务约束之一。

同一个：

```text
signal_id
```

只能执行一次。

即使出现以下情况，也不能重复下单：

* 服务器重复通知
* 客户端重复收到通知
* 客户端重启
* 网络断开后重新连接
* 客户端重新查询历史信号

SQLite 中必须能够明确记录：

```text
signal_id
execution_status
executed_at
```

---

## 9. 仓位处理

客户端根据服务器的目标仓位执行交易。

例如：

```text
服务器 → 多仓
客户端 → 检查当前仓位
        → 根据实际仓位决定是否开仓/调整
```

客户端不得自行改变服务器的目标方向。

实际仓位处理逻辑应与 TqSdk 当前账户状态保持一致。

---

## 10. SQLite

SQLite 用于记录：

* 服务器交易信号
* 信号获取时间
* 信号执行状态
* 实际执行时间
* 执行结果
* 错误信息

建议至少区分：

```text
pending
executing
success
failed
```

具体状态可以根据实际代码调整。

---

## 11. 网络异常

客户端必须能够处理：

* Server 不可访问
* 网络断开
* Server 重启
* 通知连接断开
* API 请求超时
* 重复通知
* 获取信号失败

网络异常不能导致客户端交易状态数据库损坏。

Server 恢复后，客户端应该能够重新连接并查询未处理信号。

---

## 12. TqSdk 异常

需要处理：

* TqSdk 连接失败
* 行情获取失败
* 下单失败
* 撤单失败
* 账户状态异常
* 网络异常
* TqSdk 重连

交易失败必须记录原因。

不能因为一次交易异常导致整个客户端无提示退出。

---

## 13. 数据一致性

交易执行必须尽量保证：

```text
收到信号
   ↓
记录信号
   ↓
检查是否执行
   ↓
执行交易
   ↓
确认执行结果
   ↓
更新 SQLite
```

必须避免：

```text
已经下单
但是客户端认为没有执行
↓
重新启动
↓
再次下单
```

这是客户端需要重点防止的异常场景。

---

## 14. 客户端启动

客户端启动后：

1. 初始化配置。
2. 初始化 SQLite。
3. 连接交易服务器。
4. 注册/提交交易品种。
5. 获取当前有效信号。
6. 检查未执行信号。
7. 连接 TqSdk。
8. 进入正常运行状态。

客户端重启后必须能够恢复之前的执行状态。

---

## 15. 运行模式

客户端属于长期运行程序。

正常情况下：

```text
启动
 ↓
连接 Server
 ↓
连接 TqSdk
 ↓
等待信号
 ↓
收到信号
 ↓
执行交易
 ↓
继续等待
```

交易信号不是高频事件，因此不需要设计复杂的高并发交易架构。

---

## 16. 平台

客户端最终支持：

* macOS `.app`
* Windows `.exe`

代码需要保持跨平台兼容。

避免使用仅支持单个平台的系统 API，除非确实有必要。

平台相关功能必须隔离。

---

## 17. 配置

以下配置不应硬编码：

* Server 地址
* Server 端口
* TqSdk 配置
* 账户配置
* 交易品种
* 日志配置
* 其他敏感信息

敏感信息不得提交到 Git。

---

## 18. 日志

至少记录：

* 客户端启动
* Server 连接
* Server 断开
* TqSdk 连接
* 收到交易信号
* 信号是否已经执行
* 下单操作
* 下单结果
* 当前仓位
* 异常
* 重连

日志需要能够还原：

> 为什么这个交易信号最终产生了这笔交易。

---

## 19. 测试要求

修改交易相关代码后必须测试。

至少覆盖：

* Server 信号获取
* SQLite 信号记录
* 重复信号处理
* TqSdk 行情获取
* 开仓
* 平仓
* 交易失败
* 网络断开
* Server 重启
* Client 重启
* 重复通知

特别测试：

> 客户端重启后，同一个 signal_id 不会再次执行交易。

---

## 20. 明确边界

### Server

```text
K线 / Tick
    ↓
策略计算
    ↓
多 / 空
    ↓
交易信号
```

### Client

```text
交易信号
    ↓
获取实时行情
    ↓
检查当前仓位
    ↓
TqSdk
    ↓
实际交易
    ↓
SQLite记录
```

---

## 21. 开发原则

1. 不在客户端复制服务器策略。
2. 不自行判断交易方向。
3. 不随意修改交易执行逻辑。
4. 同一个 `signal_id` 不得重复执行。
5. 交易执行状态必须持久化。
6. 优先保证交易状态一致性。
7. 优先使用简单可靠的架构。
8. 不为了低频交易场景引入复杂消息队列。
9. 保持 macOS / Windows 兼容。
10. 修改交易逻辑后必须验证。
11. 不确定业务规则时不要自行假设。
